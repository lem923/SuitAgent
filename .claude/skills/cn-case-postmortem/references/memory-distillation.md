# memory 沉淀指引

## 沉淀的目标

把单一案件的实战经验**抽象 + 去标识化**为可复用的"问题模式 + 采纳方案"，沉淀到对应
skill 的 memory.md，让下一个同类案件直接受益。

**关键原则**：
1. **抽象**：不是事实记录，是模式记录
2. **去标识化**：严禁含 client identifier
3. **可复用**：沉淀的条目必须能被其他案件直接读懂、直接借鉴
4. **人 in the loop**：所有沉淀必须经用户审阅确认后才写入

## 沉淀目标 skill 与对应位置

| 经验类型 | 沉淀到 |
|---------|--------|
| 起草中的高频问题 + 采纳方案（按文书类型）| `cn-litigation-drafting/memory.md`（如未存在则新建）|
| 合同审查中的高频问题（按 14 类合同分节）| `cn-contract-review/memory.md` |
| 要件审判九步法的归入经验 | `cn-jiubufa-case-analysis/references/memory.md`（如未存在则新建）|
| 判决书评审 / 救济路径研判经验 | `cn-judgment-analysis/references/memory.md`（如未存在则新建）|
| 庭审准备实战经验 | `cn-trial-preparation/references/memory.md`（如未存在则新建）|
| 客户沟通经验 / 决策建议有效性 | `cn-client-communications/references/memory.md`（如未存在则新建）|

## 抽象步骤（4 步法）

### Step 1：识别"事实层条目" vs "模式层条目"

**事实层条目（不沉淀）**：
- 当事人姓名、案号、合同金额、身份证号、银行账户
- 具体合同条款原文
- 具体判决主文
- 具体证据内容

**模式层条目（沉淀）**：
- 问题模式（"X 类合同中，Y 条款常被对方提出 Z 风险"）
- 采纳方案（"添加 W 表述以缓释风险"）
- 适用场景（"政企技术开发合同 + 乙方视角"）
- 法律依据（条文 + 司法解释）

### Step 2：抽象提取

对**模式层条目**做抽象：

| 原文（不沉淀）| 抽象（沉淀）|
|-------------|-----------|
| "本案中甲方北京 XX 公司主张乙方上海 YY 公司逾期交付" | "买卖合同中，买方主张卖方逾期交付时" |
| "诉讼请求金额 1234567 元" | "诉讼请求金额范围（中等额度，[10万-100万] 区间）" |
| "对方律师上海 XX 所张某" | "对方律师" |
| "甲方法定代表人王 XX" | "对方负责人" |

### Step 3：构造 memory 条目

按对应 memory.md 的格式：

```markdown
## YYYY-MM-DD [文书类型 / 合同类型 / 等] — [问题模式简述]

- **问题模式**：[抽象描述]
- **采纳方案**：[抽象描述]
- **适用场景**：[本类型 / 本视角]
- **法律依据**：[法条 / 司法解释]
- **备注**：[特殊考量]
```

### Step 4：脱敏检查

按下表逐项检查：

| 检查项 | 标准 |
|-------|------|
| 当事人姓名 | 无（仅"甲方/乙方/原告/被告"等抽象指代）|
| 案号 | 无 |
| 合同金额原文 | 无（用范围词："小额 [<10万]"、"中等 [10万-100万]"、"大额 [>100万]"）|
| 身份证号 / 统一社会信用代码 | 无 |
| 银行账户 | 无 |
| 具体地址 | 无（仅"X省 / 北上广深 / 二线城市"等粗粒度）|
| 邮箱 / 电话 | 无 |
| 内部代号 / 客户简称 | 无 |
| 同一案件内的两条以上事实拼合后能否反推案件 | 不能 |

任一未通过 → **不得沉淀**，需重新抽象。

## 沉淀条目示例（合规）

```markdown
## 2026-04-09 政企软件开发合同 — 验收条款缺失视为验收

- **问题模式**：合同仅约定"甲方验收"，无验收期限、无视为验收条款、无异议反馈机制；
                乙方视角下存在"验收无限拖延"风险
- **采纳方案**：增加"甲方应在收到交付物后 X 个工作日内完成验收并书面反馈；逾期未反馈
                视为验收通过"。X 的具体值按合同金额 / 复杂度调整：
                  - 中小金额简单项目：15 个工作日
                  - 中等金额项目：20 个工作日
                  - 大额复杂项目：30 个工作日 + 第三方验收
- **适用场景**：所有政企技术开发 / 系统集成 / 信息化采购合同（乙方视角）
- **法律依据**：民法典第 776 条（承揽合同验收）+ 司法解释相关条款
- **备注**：甲方视角时反向操作（争取较短期限 + 加详细验收标准）
```

## 沉淀条目示例（不合规，不得通过审阅）

```markdown
## 2026-04-09 北京 XX 公司 与 上海 YY 公司 政企软件开发合同纠纷 — 验收条款问题

- **问题模式**：本案中甲方北京 XX 公司在合同 [2024]京XX号中要求乙方完成
                价值人民币 1234567 元的开发任务，但合同未约定验收期限...
```

**问题**：含具体当事人名称、案号、金额——**严禁沉淀**。

## 用户审阅触发点

Postmortem agent 在 Stage 4 完成抽象后：

1. 输出"沉淀草稿"（含拟写入哪个 skill 的哪条 memory）
2. 显式询问用户："以下草稿是否同意沉淀？"
3. 用户审阅（重点：脱敏检查 + 抽象准确性 + 是否真正可复用）
4. 用户回复：
   - "全部同意" → 写入所有
   - "部分同意" → 用户指明哪些 / 哪些需修改
   - "重做" → 重新抽象
5. 用户确认后 agent 才写入对应 skill 的 memory.md

## 沉淀的边界

**不沉淀的内容**：
- 客户特定偏好（属于 personal-preferences.md，不是 memory）
- 律师团队个人风格（属于 personal-preferences.md）
- 律所内部流程（属于律所文档系统）
- 单次性事件（如某法官的临时性偏好）
- 案件特殊事实（如客户与对方有私人纠纷）

**沉淀的内容**：
- 类案普遍存在的问题模式
- 在多案中验证有效的采纳方案
- 法律依据稳定的法理或司法解释解读
- 谈判 / 庭审中的可复用技巧

## 沉淀质量评估

每年（或每 10 个 sustained 案件后）评估 memory.md 质量：

- 条目数 / 案件数 比率：合理范围 0.3-1.0（不每案沉淀，但有足够积累）
- 条目复用率：被后续案件实际引用的比率（≥30% 算合理）
- 条目老化：超过 3 年未被引用的条目，考虑废弃或归档
