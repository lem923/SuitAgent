# New Case · 创建与重整理案件文件夹

按 SuitAgent v1.10.1+ 案件目录结构建立或重整理案件框架。**dual-mode** skill：

- **Mode 1：创建模式**——从空白生成新案件框架
- **Mode 2：重整理模式**（v1.10.1+）——对已有案件文件夹做合规检查 + 命名规范化 + 内部结构整理

> 案件目录结构权威定义见 `.claude/rules/AgentMapping.md`；案件命名规范权威定义见 `.claude/rules/OutputStandards.md` 的"案件文件夹命名规范"段。

## 模式判定

| 输入 | 模式 |
|------|------|
| 用户说"新建案件 / 创建新案件 / 接了个新案"+ 提供案件信息 | **Mode 1：创建** |
| 用户说"整理这个案件 / 重命名案件文件夹 / 案件归一化 / 这个文件夹结构乱" | **Mode 2：重整理** |
| 已存在案件目录但文件夹名不符合 `YYMMNN 原告 与 被告 案由` 格式 | **Mode 2：重整理** |
| 已存在案件目录且名称合规，但内部结构（11 numbered slots + matter triplet）缺失 | **Mode 2：重整理** |

## 案件命名规范（严格）

格式：`{YYMMNN} {原告简称} 与 {被告简称} {案由}`

| 字段 | 规则 |
|------|------|
| **YYMMNN** | 年月顺序号，6 位数字（年 2 位 + 月 2 位 + **当月案件自然顺序号 2 位**）|
| 空格 | 字段间用**单个空格**分隔 |
| **原告简称** | 不超过 6 字；多原告取最重要 1 个或用"等"（如`王某 等`）；公司用全称简化（"华雄公司"/"北京 XX 局"）|
| **与** | 单字分隔，前后各一空格 |
| **被告简称** | 同原告简称规则 |
| **案由** | 标准案由名（参《民事案件案由规定》），不超过 10 字 |

### NN（自然顺序号）规则

- NN = **本所当月内案件按收案时间顺序递增**（不按字母 / 案由 sort，不按客户首字母）
- 从 **01 起算**，每月独立重置
- **不跳号**：同月已有 260501-260507，下一个新案件就是 260508
- 一旦使用不回收：即使案件撤销 / 弃案，该编号不复用
- 重整理模式下检测当月已用 NN，建议下一个未用编号

### 特殊场景

| 场景 | 命名变体 |
|------|---------|
| 行政诉讼 | `{YYMMNN} {原告} 诉 {行政机关} {案由}`——用"诉"替代"与" |
| 婚姻家事 | 通常双方都是当事人，保留双名：`{YYMMNN} {夫} 与 {妻} 协议离婚` |
| 多原告 | 取最重要的或用"等"：`{YYMMNN} 王某 等 与 {被告} {案由}` |
| 多被告 | 同上：`{YYMMNN} {原告} 与 李某 等 {案由}` |
| 仲裁 | `{YYMMNN} {申请人} 与 {被申请人} 仲裁`（不用"诉"或"与"以外的字）|
| 涉外 / 跨境 | 当事人按当地实务习惯简化（如 HK 上市公司可用 ticker + 简称）|
| **合同审查（contract-review profile）** | `{YYMMNN} {客户简称} {合同类型}审查`（无原被告/案由概念）；例 `260601 某科技 股权转让合同审查`；有明确交易对手时 `{YYMMNN} {客户} 与 {对方} {合同类型}审查` |

### 标准例

```
260221 张家宁 与 pokebone 模型 著作权
260315 甲公司 与 乙公司 合同纠纷
260509 王实 与 王琨 协议离婚
260512 北京 XX 局 诉 王某 行政处罚
```

### 反例

```
❌ 260507 华雄公司 土地使用权转让纠纷       （缺 "与 被告"）
❌ 260508 赵利平劳动纠纷                    （字段间无空格）
❌ 王荣 劳动纠纷                            （缺 YYMMNN + 缺 "与 被告"）
❌ 260221 王某诉李某合同纠纷                （应为 "王某 与 李某" 或行政诉讼用 "诉"）
❌ 260221 王某 vs 李某 合同纠纷             （vs 不在规范内，应为 "与"）
❌ 26022 王某 与 李某 合同纠纷              （YYMMNN 必须 6 位）
```

## Mode 1：创建模式

### 触发

- 自然语言：" 创建新案件" / "新建案件" / "新案件"
- 参数化触发：通过下表参数

| 参数 | 必需 | 说明 | 示例 |
|------|------|------|------|
| `--case-id` | 是 | 案件编号 | `260221 张家宁 与 pokebone 模型 著作权` |
| `--client-name` | 否 | 委托人姓名 / 公司名 | `北京科技有限公司` |
| `--case-type` | 否 | 案件类型 | `民事`/`刑事`/`行政`/`仲裁` |
| `--case-cause` | 否 | 案由 | `合同纠纷` |
| `--opposite-party` | 否 | 对方当事人 | `上海 XX 公司` |
| `--input-dir` | 否 | 客户提供材料的源目录 | `/path/to/materials` |

### 案件根目录结构（生成目标，**按 matter.yaml `项目类型` 分两 profile**）

**5 件 root 文件两 profile 通用**：matter.yaml / matter_dashboard.md / AGENTS.md / 工时记录.md / handoff_ledger.md（均必生成）。numbered slots 按 profile 分支：

**profile A — 诉讼（litigation，默认；11 numbered slots，与既往完全一致，零改动）**
```
{YYMMNN 原告 与 被告 案由}/
├── （5 件 root 文件，见上）
├── 00 - 客户提供/
├── 01 - 委托材料/
├── 02 - 法律研究/
│   └── 案件分析/
├── 03 - 我方证据/
├── 04 - 对方证据/
├── 05 - 我方法律文书/
├── 06 - 对方法律文书/
├── 07 - 法院法律文书/
├── 08 - 庭审笔录/
├── 09 - 参考文件/
├── 10 - 综合报告/
└── 99 - 复盘沉淀/
```

**profile B — 合同审查（contract-review；7 numbered slots，对齐 cn-contract-review 4-stage）**
```
{YYMMNN 客户简称 合同类型审查}/
├── （5 件 root 文件，见上）
├── 00 - 客户提供/          ← Prepare 输入：待审合同原件 + 附件 + OCR
├── 01 - 委托材料/          ← 委托书 / 服务协议（独立委托时；可空）
├── 02 - 审查报告/          ← Review：7-section 报告 + RED/ORANGE/YELLOW + fallback三档 + 签署前清单
├── 03 - 谈判轮次/          ← Discuss：对方回应 + 逐轮修改 + 版本对比
├── 04 - 红线与交付/        ← Execute：红线版 DOCX + 审查意见书终稿（_FINAL/_SIGNED）
├── 09 - 参考与playbook/    ← playbook + 同类合同范本 + 相关法规监管
└── 99 - 复盘沉淀/          ← Learn：案件侧复盘（可复用经验另沉淀进 cn-contract-review/memory.md）
```
> 合同审查 profile **不创建** 03-我方证据 / 04-对方证据(诉讼语义) / 05-08 文书法院庭审 / 10-综合报告 等诉讼专属空 slot；09/99 保留与诉讼同号习惯统一（语义按 profile 解释）。

### 创建工作流（5 步）

```
Step 1：分析输入材料 + 项目类型判定
  → 扫描案件文件夹，列出所有文件
  → 识别材料类型：法律服务方案 / 沟通记录 / 证据材料 / 委托材料 / 身份证明 / 待审合同 / 其他
  → 提取关键信息：当事人 / 案件类型 / 案由 / 涉案金额 / 对方主体
  → **判定项目类型 profile（决定目录结构 + 命名规范）**：
      - **合同审查（contract-review）**：信号词=合同审查/审阅/红线/把关/签署前/
        pre-signing/"这份合同有没有问题/有没有坑" 且**无诉讼语境**
        （无 起诉·答辩·法院·案号·开庭·仲裁·再审·监督）
      - **诉讼（litigation，默认）**：诉讼/仲裁/起诉/答辩/再审/检察监督/...
      - **歧义**（既像合同审查又含诉讼语境，如"合同纠纷起诉"）→ 主动问用户一句：
        "这是诉讼/仲裁案件，还是签署前/风险层面的合同审查项目？"
      - 判定结果写入 matter.yaml `项目类型` 字段（合同审查 | 诉讼）

Step 2：合规命名（按 profile 选规范）
  → **诉讼 profile**：`{YYMMNN} {原告} 与 {被告} {案由}`（及特殊场景变体）
  → **合同审查 profile**：`{YYMMNN} {客户简称} {合同类型}审查`
    （例：260601 某科技 股权转让合同审查；有明确交易对手时可
     `{YYMMNN} {客户} 与 {对方} {合同类型}审查`）
  → NN 项自然编号：扫描项目根目录已有 YYMMNN 文件夹，确定本月当前最大 NN，新案件用 NN+1
    （NN 序列两 profile 共用同一月度序号池，不分开计）
  → 缺字段时主动询问用户（诉讼：YYMMNN/原告/与/被告/案由；合同审查：YYMMNN/客户简称/合同类型）

Step 3：建立标准目录结构（按 matter.yaml `项目类型` 分支）
  → **诉讼 profile**：创建 11 个 numbered slots（00-10 + 99）+ 02 案件分析子目录
  → **合同审查 profile**：创建 7 个 numbered slots（00 客户提供 / 01 委托材料 /
     02 审查报告 / 03 谈判轮次 / 04 红线与交付 / 09 参考与playbook / 99 复盘沉淀），
     **不创建** 03-我方证据/04-对方证据/05-08/10 等诉讼专属 slot
  → 两 profile 均不创建超出本 profile 定义的 slot（不删除项目根 .gitignore 的兜底）

Step 4：生成 5 件 root 文件
  → matter.yaml（结构化操作数据；schema 见 references/yaml-schema.md）
  → matter_dashboard.md（人读看板；模板见 references/case-info-template.md）
  → AGENTS.md（per-case agent 边界；模板见 cn-litigation-case-folder-organizer 中 AGENTS.md 模板段）
  → 工时记录.md（工时模板见 references/timesheet-template.md）
  → handoff_ledger.md（v1.13.0；预建空 schema 头：标题 + 说明引 .claude/rules/HandoffProtocol.md
     + 一行"（暂无 briefing，由各 producing agent 落盘后倒序追加）"占位）

Step 5：材料分类入位
  → 按下表把客户提供的材料移到对应 slot

**诉讼 profile**：

| 材料类型 | 目标 slot |
|---------|----------|
| 客户递交的原始材料 | `00 - 客户提供/` |
| 委托代理协议 / 授权委托书 / 谈话笔录 | `01 - 委托材料/` |
| 我方手头的证据 | `03 - 我方证据/` |
| 对方提交的证据 | `04 - 对方证据/` |
| 法院送达的传票 / 裁定 / 判决 / 调解书 | `07 - 法院法律文书/` |
| 庭审记录 | `08 - 庭审笔录/` |
| 参考法条 / 判例 / 模板 | `09 - 参考文件/` |

**合同审查 profile**：

| 材料类型 | 目标 slot |
|---------|----------|
| 待审合同原件 / 附件 / OCR | `00 - 客户提供/` |
| 委托书 / 服务协议（独立委托时）| `01 - 委托材料/` |
| 对方回应 / 修改稿往来 | `03 - 谈判轮次/` |
| 同类合同范本 / playbook / 相关法规监管 | `09 - 参考与playbook/` |
（审查报告/红线版由 ContractReviewer 产出，落 `02 - 审查报告/` 与 `04 - 红线与交付/`）
```

## Mode 2：重整理模式（v1.10.1+）

### 触发

- 自然语言：" 整理这个案件" / "重命名案件文件夹" / "这个文件夹乱" / "case folder organize" / "案件归一化"
- 参数化：`--reorganize <现有文件夹路径>`
- 自动检测：用户在已有案件目录内调起本 skill，且文件夹名不符合命名规范，或内部结构缺失关键元素

### 重整理工作流（7 步）

```
Step 1：现状扫描
  → 读取当前文件夹完整路径与名称
  → 解析当前文件夹名（拆解 YYMMNN / 原告 / 与 / 被告 / 案由）
  → 扫描内部文件结构：是否含 11 numbered slots / matter triplet / 工时记录 / 旧 12 层 emoji 目录 / 客户提供的散落材料

Step 2：命名合规检查
  → 检查项：
      [a] 是否有 YYMMNN 6 位前缀
      [b] 字段间是否用单个空格分隔
      [c] 是否含"与"分隔符（行政诉讼用"诉"）
      [d] 原告简称 / 被告简称是否清晰
      [e] 案由是否为标准案由名
  → 输出合规报告：通过项 ✅ / 不通过项 ❌ + 具体不合规原因

Step 3：缺字段询问（人 in the loop）
  → 对每个 ❌ 的字段，向用户明确询问：
      "您本案的 [字段名] 应该是什么？"
  → NN 自动建议：
      → 扫描项目根目录已有 YYMMNN，识别当月最大 NN
      → 建议下一个未用编号
      → 用户可手动覆写（如该案件实际收案日期对应的 NN 不同）
  → 用户确认后再进入 Step 4

Step 4：生成 mv 命令 + 用户确认
  → 生成命令：
      mv "<原文件夹路径>" "<新合规文件夹路径>"
  → 显式输出到对话内，等待用户明确执行
  → ⚠️ 不自动 mv（保密硬约束 + 客户案件不可逆操作必须人 in the loop）

Step 5：内部结构整理
  → 缺 matter triplet → 生成（同 Mode 1 Step 4）
  → 缺 11 numbered slots → 创建空目录
  → 含旧 12 层 emoji 目录（00 - 📅 日程管理 等）→ 迁移内容到新 slot（按 AgentMapping v3.0+ 映射表）
  → 散落在根目录的客户材料 → 移到对应 slot
  → 调起 cn-litigation-case-folder-organizer skill（外置）的 Move 阶段（如可用）

Step 6：matter.yaml 字段更新
  → `matter_id` ← 新合规案件名
  → `当前阶段` ← 视实际状态（"立案中" / "答辩期" / 等）
  → `关键日期` ← 从原文件夹扫描到的法院送达 / 期限信息

Step 7：完成标识
  → 响应末尾输出：原文件夹名 → 新文件夹名 / 内部结构状态（11 slot 完整度）/ matter triplet 状态 / 待用户配合事项

### 重整理模式的禁忌

- ❌ 不自动执行 mv（必须用户明确确认；生成命令但不跑）
- ❌ 不删除任何原始文件（仅 mv / mkdir / cp，不 rm）
- ❌ 不在文件名后缀含 `_FINAL` / `_SIGNED` / `_盖章` 等的文件上 mv（参 CLAUDE.md 文件操作默认）
- ❌ 不跨 matter 移动文件（保密硬约束）
- ❌ 不臆造缺失字段（YYMMNN / 对方 / 案由 缺则询问，不自动补造）
```

## 关键规则

### 案件编号规则（重申）

格式：`{YYMMNN} {原告简称} 与 {被告简称} {案由}`

详见上文"案件命名规范（严格）"段。

### NN 自然编号实施细节

```
get_next_nn(year, month):
    existing_dirs = glob(project_root + "/<year><month>*/")
    used_nns = []
    for d in existing_dirs:
        match = re.match(r"^(\d{2})(\d{2})(\d{2})\s", d.name)
        if match and match.group(1) + match.group(2) == year + month:
            used_nns.append(int(match.group(3)))
    if not used_nns:
        return "01"
    return f"{max(used_nns) + 1:02d}"
```

实施时：
1. 跳过非 YYMMNN 起头的目录（如 "王荣 劳动纠纷"——这种本身就违反命名规范，应进入重整理）
2. NN 取当月最大已用 + 1
3. 即使中间有跳号（如 260501 / 260503 / 260505），下一个建议 260506（按最大值递增）

### 文件命名规则

- matter.yaml / matter_dashboard.md / AGENTS.md / 工时记录.md：root level 固定名，无日期前缀
- 各 slot 内一次性输出文件：`YYMMDD [文书类型].md`（详见 OutputStandards.md）
- 文件名一律 UTF-8，不改 GBK / 拼音 ASCII

## 时间要求

使用系统当前时间 `date "+%Y-%m-%d"`：
- matter.yaml 的 `创建日期` / `更新日期` 字段为当前日期
- matter_dashboard.md 的"更新历史"首条为当前日期
- 时间线逻辑正确（过去→现在→未来）
- 关键日期剩余天数计算准确
