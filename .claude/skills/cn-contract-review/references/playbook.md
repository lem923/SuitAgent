# Playbook · 组织/审查人标准立场配置

> **v1 状态**：本文件 v1 阶段仅留**骨架 + 字段说明**。审查人（项目维护者或律所同事 fork 后）
> 按需填入自己的标准立场。Stage 0 加载本文件时，未填字段降级为 checklist 隐式立场（行为
> 与未引入 playbook 时一致，不退化）。

## 用法

Stage 0（Prepare）阶段读取本文件，按本案合同类型加载对应章节的"标准立场"。在 Stage 1
Step 3 微观条款扫描时，把"原合同条款 vs 标准立场"的偏差作为 ORANGE / REDLINE 的判定依据
之一（与 contract-types/ 的 checklist 互补：checklist 列"应有什么"，playbook 列"我所/
我们的立场是什么"）。

## 字段说明

每个合同类型分节固定 6 字段：

| 字段 | 内容 |
|------|------|
| **核心立场** | 我方在该类合同中的根本目标（如"作为乙方追求最大付款保障 + 验收期限可控"） |
| **绝不让步条款** | Tier 1 / REDLINE 等价物，写明"出现此措辞即拒签"的具体条款表述 |
| **重要争取条款** | Tier 2 / ORANGE 等价物，写明"标准目标 / 可签底线 / 绝对底线"三档 |
| **可让步条款** | Tier 3 / YELLOW 等价物，作为谈判筹码可以让步换取更高级别条款 |
| **常见对方诉求** | 对方可能提出哪些条款，对应我方应对策略 |
| **历史经验提示** | 该类合同审查中的"踩过的坑"——参考 memory.md 同类型条目 |

## 与 personal-preferences.md 的边界

- `playbook.md` = 组织 / 团队层面的标准立场（律所或团队达成共识的口径）
- `personal-preferences.md` = 审查人个人的方法偏好与历史经验（如背靠背付款、
  通知送达、分包等问题的处理习惯）

两份文件互补：playbook 提供"应该怎么改"，personal-preferences 提供"我习惯怎么操作"。

## 维护规则

- 修改本文件后无需 skill 重启，下次合同审查时 Stage 0 加载新内容
- 不在本文件中记录具体客户名 / 案号 / 金额原文
- 字段空时降级为 checklist 隐式立场，不报错
- 同事 fork 本 skill 后，建议先把所有 yaml 块改成自己的口径，再提交 PR / 上线本地用
